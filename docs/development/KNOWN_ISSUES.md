## 결함

### D-1. 선택 입력인 외래키를 비우고 등록하면 DB 오류가 발생함

**증상**: 외래키 컬럼이 `NULL` 을 허용하는 엔티티의 등록 화면에서, 콤보 상자에서 아무것도 고르지 않고 저장하면 "데이터베이스 오류가 발생했습니다." 화면이 표시됩니다. 참조할 값을 고르면 정상으로 등록됩니다.

**원인**: 콤보 상자를 비우면 빈 문자열이 전송되고, 이 값이 `NULL` 로 바뀌지 않은 채 INSERT 에 쓰여서 외래키 제약 조건을 위반합니다. 세 스택 모두 외래키 필드의 빈 문자열을 `NULL` 로 바꾸는 처리가 없습니다.

**피하는 방법**: 참조되는 엔티티의 데이터를 먼저 등록하고, 등록 화면에서 값을 고릅니다. 프로젝트를 처음 만든 직후에는 참조할 데이터가 없어서 콤보 상자가 비어 있으므로, 이 문제를 바로 만나게 됩니다.

**고치는 방향**: 각 스택의 엔티티 Controller 에서 `NULL` 을 허용하는 외래키 필드에만 `StringTrimmerEditor(true)` 를 등록해서 빈 값을 `NULL` 로 바꿉니다. `NOT NULL` 인 외래키는 지금처럼 오류가 나는 것이 맞습니다.

### D-2. 용량을 넘는 업로드가 CSRF 접근 거부 화면으로 이어짐

**증상**: 5.1 Boot 에서 `spring.servlet.multipart.max-file-size` 를 넘는 파일을 올리면, 첨부파일 안내 화면(`cmm/uploadError`)이 아니라 CSRF 접근 거부 화면이 표시됩니다.

**원인**: CSRF 토큰이 multipart 본문의 한 파트로 전송되는데, 용량 초과로 파트 파싱이 실패하면 CSRF 필터가 토큰을 읽지 못합니다. CSRF 검사가 업로드 예외 처리보다 먼저 실행됩니다. [5.1 Boot 보안 설정](../architecture/SECURITY_CONFIG.md)의 "multipart 업로드와 CSRF"에 설명이 있습니다.

**피하는 방법**: 한도를 운영 정책에 맞게 설정하고, 화면에 한도를 안내합니다. 4.3 Boot 에는 CSRF 가 없어서 이 문제가 없습니다.

**고치는 방향**: 용량 초과를 CSRF 검사보다 먼저 구분하도록, CSRF 필터 앞에 multipart 를 처리하는 필터를 두거나 토큰을 요청 헤더로 보내는 방식을 검토합니다.

## 제약 사항

### L-1. 기본 키와 테이블 이름의 길이

자동 채번은 `<테이블 이름>-NNNNN` 형식의 값을 만들고, 채번의 현재 값을 `IDS` 테이블에 테이블 이름별로 저장합니다. 이 때문에 두 가지 길이 제한이 있습니다.

- 기본 키 컬럼은 `테이블 이름의 길이 + 6` 이상이어야 합니다. `egov_add_entity` 는 이 조건을 미리 검사해서 거부하지만, `egov_scaffold_project` 는 검사하지 않습니다. 첫 엔티티의 기본 키가 짧으면 프로젝트는 생성되고, 등록할 때 채번된 값이 컬럼 길이를 넘게 됩니다.
- 테이블 이름은 16자 이하여야 합니다. `IDS.TABLE_NAME` 이 `VARCHAR(16)` 이기 때문입니다. 두 도구 모두 이 조건을 검사하지 않습니다. 이름이 16자를 넘으면 시드 SQL 의 `INSERT INTO IDS` 가 길이 초과로 실패해서, 내장 HSQLDB 프로파일에서 프로젝트가 시작되지 않습니다.

### L-2. 복합 기본 키와 기본 키가 없는 테이블

- 복합 기본 키는 SQL 과 Mapper 의 조건절에는 반영되지만, 자동 채번과 목록 화면의 상세 이동은 첫 번째 기본 키 컬럼만 사용합니다. 복합 기본 키 테이블의 화면과 Controller 는 생성한 뒤에 직접 고쳐야 합니다.
- 기본 키가 없는 테이블은 지원하지 않습니다. 도구가 이런 DDL 을 거부하지는 않으므로, 기본 키를 선언했는지 확인하고 호출합니다.
- 외래키는 컬럼 하나짜리만 인식합니다.
- 타입 표에 없는 컬럼 타입은 `java.lang.Object` 로 매핑됩니다. [DDL 입력 규칙](../reference/DDL_INPUT.md)의 타입 표를 참고합니다.

### L-3. Oracle 계열 DBMS 로 전환할 때 SQL 을 직접 고쳐야 함

테이블을 만드는 SQL 은 7개 DBMS 용으로 생성되지만, MyBatis 의 조회 SQL 은 한 가지 형태로만 생성됩니다. 목록 조회의 페이징 구문(`LIMIT ... OFFSET ...`)과 검색 조건의 `CONCAT('%', ..., '%')` 는 HSQLDB, MySQL, MariaDB, PostgreSQL, CUBRID, Goldilocks 에서 동작하고, Oracle, Tibero, Altibase 에서는 동작하지 않습니다. 이 DBMS 로 전환할 때에는 각 SQL 파일의 주석에 적힌 구문으로 직접 바꿔야 합니다. 첨부파일 인프라의 SQL 에 있는 `SYSDATE()` 와 `IFNULL` 도 마찬가지입니다.

### L-4. 조회 화면의 SQL 을 검증하지 않음

`egov_add_query_view` 는 입력한 SQL 을 실행하거나 해석하지 않고 매퍼 XML 에 그대로 넣습니다. 검사하는 것은 `SELECT` 로 시작하는지와 `]]>` 가 없는지뿐입니다.

- SQL 의 별칭과 `columns` 의 `alias` 가 일치하는지 대조하지 않습니다.
- `LIMIT`, `OFFSET`, 문장 끝의 세미콜론이 들어 있어도 거부하지 않습니다.
- 메뉴 이름과 화면 제목에는 `viewName` 이 그대로 쓰이며, 한글 이름을 받는 인자가 없습니다. 생성한 뒤에 메시지 번들의 값을 고칩니다.
- 목록 화면의 검색 조건(`searchCondition`)은 순번으로 받습니다. 화면에서 보내지 않는 값(숫자가 아닌 값)을 직접 보내면 500 으로 응답합니다. 엔티티의 목록 화면도 같습니다.

### L-5. 인터넷에 연결되지 않은 환경에서는 달력이 뜨지 않음

날짜 입력란의 달력(flatpickr)은 CDN 에서 불러옵니다. 서버 자체는 폐쇄망에서 동작하지만, 생성된 프로젝트의 화면을 인터넷에 연결되지 않은 브라우저에서 열면 달력이 뜨지 않고 `yyyy-MM-dd` 형식으로 직접 입력해야 합니다. 세 스택 모두 같습니다.

**고치는 방향**: flatpickr 를 `templates/static50/` 에 넣어서 프로젝트와 함께 복사하고, 화면 템플릿이 로컬 파일을 불러오게 합니다.

### L-6. 첨부파일 기능의 범위

- 4.3 WAR 는 첨부파일을 지원하지 않습니다.
- 다운로드 URL(`/cmm/fms/FileDown.do`)에는 접근 제어가 없습니다. 첨부 그룹 키와 파일 순번을 아는 사용자는 누구나 파일을 받을 수 있습니다.
- 첨부파일 1건을 삭제하는 요청은 그 파일이 해당 레코드의 것인지 확인하지 않습니다. 첨부 그룹 키와 파일 순번을 아는 사용자는 다른 레코드의 첨부파일을 삭제할 수 있습니다.
- 확장자만 검사하고 파일의 실제 형식은 확인하지 않습니다. 악성코드 검사도 하지 않습니다.
- `maxAttachmentCount` 인자는 1 이상일 때 화면의 `data-max-count` 속성으로만 출력되며, 파일의 개수를 실제로 제한하지 않습니다.
- 이미 만든 엔티티에 첨부파일을 나중에 연결하는 기능은 없습니다.
- 기본값으로 설치한 인프라의 정책을 도구로 바꿀 수 없습니다. `application.properties` 의 값을 직접 고칩니다.

상세한 내용은 [첨부파일 인프라와 엔티티 연결 구조](../architecture/ATTACH_FILE.md)에 있습니다.

### L-7. 생성한 코드를 다시 생성하거나 갱신할 수 없음

도구는 새 파일을 만들기만 하고, 이미 만든 엔티티의 코드를 고치지 않습니다. 테이블에 컬럼을 추가했을 때 기존 엔티티의 코드에 반영하는 기능이 없습니다.

- 엔티티를 다른 내용으로 다시 만들려면 생성된 파일을 지우고 다시 호출해야 합니다. 이때 시드 SQL 과 메시지 번들에 이전에 덧붙은 내용이 남아 있으면 같은 테이블과 키가 한 번 더 덧붙습니다. 시드 SQL 에 같은 테이블이 두 번 있으면 내장 HSQLDB 가 시작할 때 오류가 발생하므로, 이전에 덧붙은 부분을 먼저 지웁니다.
- 서버의 버전을 올려도 이전 버전으로 만든 프로젝트의 코드는 바뀌지 않습니다. 이전 버전으로 만든 프로젝트에 새 버전의 도구로 엔티티를 추가하는 경우의 호환성은 보장하지 않습니다.

### L-8. 인증과 권한 관리가 없음

생성되는 프로젝트에는 로그인과 권한 관리가 없습니다. 5.1 Boot 의 Spring Security 설정은 보안 응답 헤더, CSRF, 방화벽, CORS 를 다루며, 모든 요청을 인증 없이 허용합니다. 4.3 의 두 스택에는 Spring Security 와 CSRF 보호가 없습니다. 운영하기 전에 프로젝트에 맞는 인증 체계를 추가해야 합니다.

## 서버의 문제와 후속 작업

### M-1. 일부 오류 문구에 절대 경로가 들어감

오류 문구에는 절대 경로를 넣지 않는 것이 이 저장소의 방침입니다. 파일 쓰기 실패와 첨부파일 인프라 설치 실패의 문구는 프로젝트의 절대 경로를 `<projectDir>` 로 바꿔서 출력합니다. 그러나 다음 문구에는 경로가 그대로 들어갑니다.

- 프로젝트 감지 실패 (`projectDetector.ts`): "projectPath 가 존재하지 않거나 접근할 수 없습니다: <경로>" 등
- 기본 패키지 감지 실패, 템플릿 파일을 찾지 못한 경우, 스택 정의 파일을 읽지 못한 경우
- `egov_scaffold_project` 의 자체 검증 실패
- 매니페스트 파일을 읽지 못하거나 해석하지 못한 경우 (`manifestLoader.ts`)

이 경로들은 호출한 쪽이 인자로 넘긴 경로이거나 서버가 설치된 경로입니다. 성공했을 때의 결과 메시지도 프로젝트의 경로를 그대로 보여 줍니다.

### M-2. 5.1.0 배포 파일에 사용하지 않는 모듈이 들어 있음

`egovframe-mcp-codegen-5.1.0.tgz` 에는 `build/utils/scaffold/skillsEmitter.js` 가 들어 있습니다. 소스에서는 삭제된 모듈이며 어디에서도 불러오지 않으므로 동작에는 영향이 없습니다. `tsc` 가 `build/` 를 비우지 않고 덮어쓰기만 해서, 이전에 컴파일한 결과가 남은 것입니다. 다음 버전부터는 [배포 패키지 제작 가이드](../operations/PACKAGING_GUIDE.md)의 절차대로 `build/` 를 지우고 묶습니다.

### M-3. 테스트 코드의 타입 오류

`npx tsc -p tsconfig.tests.json` 으로 테스트 코드의 타입을 검사하면 `tests/elicitationIntegration.test.ts`, `tests/scaffold/attachmentDecision.test.ts`, `tests/scaffold/scaffoldDecision.test.ts` 에서 오류 18건이 보고됩니다. vitest 는 타입을 검사하지 않고 실행하므로 테스트는 모두 통과합니다. 이 검사는 `npm test` 에 포함되어 있지 않습니다.

### M-4. 코드의 주석과 안내 문구가 실제 동작과 다른 곳

동작에는 영향이 없지만, 코드를 읽을 때 혼동을 줄 수 있는 곳입니다.

| 위치 | 적힌 내용 | 실제 동작 |
|------|-----------|-----------|

| `src/index.ts` 의 `autoApplyProperties` 설명 | `false` 이면 추가해야 할 키를 안내 | 건너뛴 파일만 알리고 키의 목록은 출력하지 않음 |

### M-5. MCP SDK v2 로의 전환

서버는 `@modelcontextprotocol/sdk` 1.29 를 사용합니다. SDK v2 에서는 패키지 구성, 핸들러의 인자, 사용자 확인의 호출 방식이 달라집니다. 전환할 때 고칠 내용은 [MCP SDK v2 전환 가이드](./SDK_V2_MIGRATION.md)에 정리되어 있습니다. `egovframe-mcp-check`, `egovframe-mcp-search` 도 같은 SDK 를 사용하므로 세 저장소의 전환 시점을 함께 정해야 합니다.
